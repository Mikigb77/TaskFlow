# Why a run took 19 hours, and what changed (2026-11-01)

The owner, after the 2026-10-28-app plan and its website plan took about 19 hours to carry out in a cloud session: "it cannot be that we are running for 19 hours … We should deploy all the agents that can be possibly deployed at the same time, if needed." Measured from the session's agent transcripts (`scripts/workflow_timing.py` does the same on the PC).

## Where the time went

| Part | Hours |
|---|---|
| App fix runs: b1 3.9, b2 5.9, b3 3.8, then the 2026-11-01-screens follow-up 1.3 | 14.9 |
| Website fix run b1 (still running when measured) | 3.1+ |
| Planning (app re-plan 0.7, website re-plan 0.6) and gaps | 1.4 |

Inside the app fix runs: implementing (waves, package testers, merges) 67%, round checks 20%, final checks 4%, verification 5%, re-plans, records and loading 5%.

## Why

1. **Two agents at a time, all the way.** The workflow runtime runs at most min(16, CPUs − 2) agents per workflow and queues the rest. The cloud session has 4 CPUs, so every run peaked at 2 agents, whatever `maxParallel: 12` said. 1,240 agent-minutes of app work could never finish in less than about 10 hours.
2. **Waves and rounds are barriers.** A wave waited for its slowest package before anything merged; packages that shared a file went in later waves, so the longest chain of packages on one file was 195 minutes on its own. Every round waited for the round check, the verifiers and the re-plan before the next began.
3. **Redo rounds.** b1 needed 2 rounds and b2 and b3 3 each; the extra rounds, their checks and the follow-up run were about 6 hours.
4. **The same tests, again and again.** `flutter test` took 465 agent-minutes, 37% of all agent time: implementers averaged 4.8 minutes of it each, refreshing previews and rerunning tests their tester then ran again. The whole suite takes 12.7 minutes alone on 4 CPUs (16–25 sharing the machine), and it ran in 9 round checks and 2 final checks.
5. **Failures that serialized everything.** b3's session had drifted out of the repo, so its worktrees failed and all its packages ran one at a time (almost 4 hours). In b2 one merge command failed for the whole wave, and 7 packages were redone one by one in the main checkout (36 minutes).

Not a cause: the models. Implementers averaged 9 minutes, of which about 3.4 were thinking; verification 2.7. A smaller model would have saved minutes and risked rounds.

## What changed

- **No waves, no batches.** Every package flows through on its own: implement, test, verify, one fix and a second check if it falls short, merge. It starts as soon as its `dependsOn` are merged; an earlier package's next step goes first, so packages finish one by one. At most two packages change one file at once; the three-way merge brings their edits together.
- **Fix in place, not in rounds.** The reviewer checks each package in its worktree before the merge, and its implementer fixes what falls short right there. A finding still short after that has failed twice and goes to the owner, as before. Only what fails across packages goes back to the organizer, for one more round.
- **The whole suite once per run**, with the UX previews beside it, after every package is in. Implementers run the analyzer and their covering tests only; testers run only their new tests and render the package's screens.
- **Lanes** get past the agent cap on a small machine: several `ux-fix` runs at once, each with its share of the plan (`pkg.py --lanes`), then one `finish` run. Four lanes in a cloud session give 8 agents instead of 2. Every Flutter command still waits for the shared gate.
- **Robustness:** the load step stops the run if its worktree isn't one of this repo's (the b3 failure). A merge reports each package's error on its own and never fails the others (the b2 failure); merging again after a resume gives the same answer; seeding twice can't wipe a package's work; seeds and merges share a lock; a conflicting package is carried into a fresh worktree (`waves.py carry`) instead of being redone; a package whose tests still fail is set aside with its patch, so it can't stop the run's commit. Every merge is logged in the run folder (`merges*.jsonl`).
- **Small model, low effort** for loading the plan and merging; medium effort for the record.

`flutter test --experimental-faster-testing` was tried and doesn't work for this app: its combined test file can't resolve `package:agenda` imports.
